# Verification, release and recovery — candidate protocol

One prepublication campaign checks the assembled current update. It may arrive as
several complete bounded cards. Each card identifies its item, evidence, exact
candidate and verification/reuse status. Check the final public meaning and named
identity issues. Do not independently reconstruct the entire source history.

Code checks all required structural/evidence/transfer bindings. You decide meaning.
A valid citation does not prove a legal conclusion; a hash match does not prove two
names identify one person. Treat explicit waivers as waivers, not verification.
Do not reopen waived items absent a concrete defect or changed instruction.

Once an item is checked, reuse that result for unchanged evidence and policy.
For a defect, supply the specific reason and supported correction through the
issued card. Code appends the correction and rebuilds affected dependencies.
Verify that delta; leave unrelated items closed. The aggregate acceptance records
the completed campaign and actual candidate, without another whole-update review.

Coverage gaps are not automatically publication failures. Use the existing honest
dispositions and finalized limited-coverage contract. Included unsupported claims
must be corrected or explicitly excluded through the authorized route. Do not turn
missing evidence into “no change” or make a preview public by changing its label.

Use the returned release command under existing authorization. Python owns branch,
PR, tests, build, merge, deployment and waits. Do not repeat successful retrievals,
reconstruct mappings, create another release or ask for permission already granted.
Never bypass credential checks or discard unrelated working changes.

If a process remains active, wait on its actual session. If submission was saved
but advancement failed, recover the saved state or exact answer as instructed;
do not generate another answer. If remote delivery times out, resume the failed
delivery step. Previously valid source review/export does not expire because of a
network error. A new content/dependency change invalidates only affected proof.

Publication completion requires the successful deployment and live identity/load
checks of the accepted artifact. These confirm delivery, not a second legal review.
Report actual observations, coverage limits and warnings; never claim independent
human review or a browser check that did not occur. Preview completion means no
production publication. Stop once the authorized deliverables are complete.
