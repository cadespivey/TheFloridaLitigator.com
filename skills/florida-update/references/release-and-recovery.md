# Verification, release and recovery

The prepublication campaign replaces the former substantive publication approval.
It can group items on bounded cards. Each item retains its evidence, candidate and
verification status. Use the supplied evidence to check final public meaning and
named identity issues.

Code checks all required structural/evidence/transfer bindings. You decide meaning.
A valid citation does not prove a legal conclusion; a hash match does not prove two
names identify one person. Treat explicit waivers as waivers, not verification.
Do not reopen waived items absent a concrete defect or changed instruction.

On a `publication_verification` card, choose `verify` and supply the I-reference and a substantive reason for each item checked. A partial result closes those items. On `correct`, identify the affected opinion and supply its changed fields and reason. The same reply may verify the sound items. An `unresolved` reply checkpoints the current card. When an oversized card points to its packet, read the complete indicated item before deciding.

Once an item is checked, reuse that result for unchanged evidence and policy.
For a defect, supply the specific reason and supported correction through the
issued card. Code appends the correction and rebuilds affected dependencies.
Verify that delta; leave unrelated items closed. The aggregate acceptance records
the completed campaign and actual candidate, without another whole-update review.

Use the existing disposition for an unavailable acquisition and leave it in the
internal record for the next run. Available unfinished reviews, pending source
corrections and substantive review exceptions block finalization. Correct or use
the authorized exclusion route for an unsupported included claim. An acquisition
failure stays open until resolved and never establishes “no change.”

Use the returned release command under existing authorization. It passes the
reviewed report and directory bundle to the existing Pages workflow. Python owns
branch, PR, tests, build, merge, deployment and waits. Keep the existing credential
checks and unrelated working changes.

If a process remains active, wait on its actual session. If submission was saved
but advancement failed, recover the saved state or exact answer as instructed;
do not generate another answer. If remote delivery times out, resume the failed
delivery step. Previously valid source review/export does not expire because of a
network error. A new content/dependency change invalidates only affected proof.

Publication completion requires successful deployment and the existing live data
identity and load checks for the accepted release.
Report actual observations, coverage limits and warnings; never claim independent
human review or a browser check that did not occur. Preview completion means no
production publication. Stop once the authorized deliverables are complete.
